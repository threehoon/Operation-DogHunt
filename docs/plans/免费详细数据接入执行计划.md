## 1. 这次要做成什么

先用免费来源积累 NBA 每场球队、球员的详细数据，再用程序计算近期表现和估算指标，最后交给 AI 结合盘口与伤病分析。用户先审查本计划，确认后再按阶段执行。

可以把这件事理解为：先补齐账本，再计算报表，最后讨论如何决策。数据多不等于预测必然更准；本轮先保证数据可追溯、计算正确、分析确实用上数据。

完成后应能做到：

- 查询某队本赛季、近 5 场、近 10 场、主客场的基础表现和样本数量。
- 查看球员每场出场时间、投篮、得分、篮板、助攻、失误等，观察近期使用情况。
- 区分得分变化来自比赛节奏还是进攻表现；推算出来的指标明确标注“估算”。
- 分析一场比赛时，AI 能引用具体数字、统计区间、来源和缺失情况。
- 更新中断后可以继续，失败有记录；同一场比赛不会重复计入统计。

本计划里的目录、默认参数和验收门槛都是待审查的实施建议，不表示已经开发完成。

## 2. 已确认的边界

| 项目 | 本轮范围 |
| --- | --- |
| 数据费用 | 新增来源限无需购买的数据；不升级套餐，不购买历史数据 |
| 赛事 | NBA；常规赛优先，季后赛、附加赛单独分类；不混入季前赛、全明星赛 |
| 时间范围 | 先补 2026–27 赛季截至执行时已结束的比赛，再补 2025–26 赛季；赛季字段需核对供应商口径 |
| 比赛阶段 | 赛前分析；第一版详细统计只采纳已结束比赛 |
| 获取方式 | 人工启动一次采集任务；支持指定日期、请求上限与断点续跑，暂不设置定时任务 |
| 现有来源 | 保留 The Odds API、BALLDONTLIE、ESPN 伤病；新增详细统计不依赖刷新盘口 |
| 网站改动 | 本轮先做采集、计算和聊天接入；不新增完整数据中心页面，不重做现有页面 |
| 暂缓内容 | 新闻抓取、预计首发、逐回合数据、投篮坐标、五人阵容效果、复杂伤病价值模型 |
| 预测调整 | 先增加可核实依据，不凭少量样本制定新的自动权重或宣称准确率提升 |

免费指新增体育数据的获取不购买套餐；电脑资源、网络和既有模型调用仍可能有成本。本轮离线验证不调用模型；真实模型验收如需付费，单独说明范围与次数后由用户确认。

NBA Cup 比赛如果同时属于常规赛，只计一次；其他特殊比赛按实际赛事分类保留。常规赛和季后赛不得直接合成一个赛季平均值。

## 3. 当前基础与已经发现的问题

### 3.1 代码里已经有什么

- `backend/app/integrations/espn.py`：目前只负责伤病请求。
- `backend/app/services/odds/schedule.py`：取近 30 天赛程和比分；不是完整赛季明细库。
- `backend/app/services/odds/team_form.py`：从比分计算战绩、得失分、净胜分等。
- `backend/app/services/odds/board.py`：更新盘口后后台取赛程和伤病。
- `backend/app/services/chat/odds_context.py`：只在选场或聚焦到不超过 3 场比赛时附带详细资料。
- `backend/app/services/chat/service.py`：聊天读取本地快照，不在聊天过程中自动刷新外部数据。

这里描述代码能力，不代表当前机器已保存完整或最新的数据。现有“三场以内附带详细资料”的限制保留，避免把整个赛季塞进每次聊天。

### 3.2 免费来源的实际证据

2026-11-14 已完成小范围只读抽查，原始记录见 [数据源讨论交接](../handoff/2026-11-14-数据源扩展初步讨论.md)。

| 候选 | 实测结果 | 本轮用途 |
| --- | --- | --- |
| ESPN 比赛列表 | 请求 2026-04-10 返回 HTTP 200、15 场比赛 | 发现比赛，取得 ESPN 比赛编号 |
| ESPN 单场详情 | 比赛 `401811026` 返回 HTTP 200、2 队统计、29 行球员记录 | 第一候选详细数据来源；记录行不等于实际出场人数 |
| NBA 官方 CDN | 当日赛程文件返回 HTTP 403，访问被拒绝 | 不作为本轮必要依赖；不绕过限制 |
| BALLDONTLIE | 项目已有赛程和比分接入 | 对重叠范围做比赛、比分核对；不假定详细统计免费 |

ESPN 是可公开访问但缺乏稳定接口承诺的入口；单场成功不能证明整季完整、长期免费或适合任意频率批量请求。执行前核对公开使用说明及可用范围；出现明确限制时停止对应采集，保留已有数据并报告。

### 3.3 执行前需要确认的环境问题

最新 [后端 API 检查交接](../handoff/2026-11-14-后端API调用检查.md) 记录了 `NO_PROXY` 中 IPv6 地址写法导致 `httpx.InvalidURL` 的问题。`NO_PROXY` 是“哪些地址不走代理”的名单；HTTP 客户端可能在联网前就解析失败。

该记录还指出当时未发现本机伤病快照，赛程仍是旧文件。因此普通只读请求成功，不能替代项目自身运行环境的验证。

执行时先核实问题是否已由其他工作修复。如果仍存在，先明确项目所需代理行为，在项目范围内修正并验证；不直接关闭所有代理、不修改全局网络配置。若有多个影响用户网络的处理方案，先说明取舍再确认。

## 4. 要保存哪些数据

API 是供程序读取数据的入口；原始响应是供应商原样返回的内容，标准化数据是我们统一字段名和单位后的版本。两者都保留，方便查错和以后重新计算。

| 类别 | 第一版字段 | 规则与用途 |
| --- | --- | --- |
| 来源信息 | 来源、来源比赛编号、采集时间、来源更新时间（有则存）、解析版本、原始文件位置 | 每项统计能找到出处；没有来源更新时间时不能拿采集时间冒充 |
| 比赛信息 | 赛季、赛事阶段、主客队编号、开赛时间、来源日期、状态、比分、节数或加时信息 | 区分比赛类型、延赛和加时；不能把未结束比赛用于赛后统计 |
| 球队进攻 | 得分；投篮、三分、罚球的命中与出手；助攻、失误 | 命中率优先由命中/出手计算，便于核对 |
| 球队篮板与防守 | 进攻篮板、防守篮板、总篮板、抢断、盖帽、犯规；同场对手数据 | 双方数据配对，计算对手表现与篮板情况 |
| 球队补充 | 快攻得分、内线得分、失误得分等 | 有则保留，缺少这些不阻断核心数据入库 |
| 球员信息 | 来源球员编号、姓名、该场所属球队、是否出场、未出场原因（有则存）、首发标记（有则存） | 以编号为主；交易前后的场次属于当时的球队 |
| 球员统计 | 出场时间、得分、投篮/三分/罚球命中与出手、篮板、助攻、抢断、盖帽、失误、犯规、正负值 | 未出场不填成“出场 0 分”；正负值不能单独当作个人实力 |
| 数据质量 | 有效/部分缺失/失败、缺失字段、冲突原因、数据覆盖区间 | 缺失值不是 0；AI 和计算程序都必须知道缺了什么 |

首发、加时、未出场原因、来源更新时间等字段尚未完成逐项实测，阶段 1 核对后标明“可稳定取得”或“暂缺”，不预先保证有。

球员出场时间统一为秒，同时保留原始文本。命中/出手必须拆开存，不能只留一个百分比。球队失误、个人失误、团队失误的含义需要核对，避免重复相加。

## 5. 数据怎样保存和更新

### 5.1 首版沿用文件保存

建议先沿用项目已有的 JSON 文件方式。JSON 是程序可直接读取的结构化文本；本轮不额外建设通用数据库。

拟新增的本机数据目录：

```text
data/basketball/
  raw/          原始响应，按来源、比赛与采集版本保留
  normalized/   整理后的比赛、球队与球员明细
  manifests/    每次任务的范围、进度、失败项和请求数量
  aggregates/   预先算好的球队与球员摘要
```

这些是执行时才创建的目录，本次仅写计划。原始大文件与运行产物加入 `.gitignore`，不上传 Git；测试仅保留必要的小样例，不包含凭证。

任务清单相当于“进货登记本”：记录哪些日期已查询、哪些比赛成功、哪些缺失、最后一次尝试结果。更正后的数据新增版本，验证成功后再更新索引；中断或坏响应不能覆盖有效旧版本。文件写入采用临时文件完成后替换索引，读取方不能读到半个文件。

聊天读取预先生成的摘要，不每次遍历整个赛季原始文件。摘要带计算版本、截止时间和输入版本；明细变动时只重算受影响的摘要。

### 5.2 比赛与球员怎样对齐

- 保存各来源自己的编号，不能认为不同来源的同一个编号就是同一场比赛。
- 球队建立 30 队的显式编号/别名对应表，复用现有名称约定。
- 对阵、主客场、时间共同匹配；改期或匹配到多场时标记冲突，不随便取第一场。
- 球员以来源编号为主；伤病只有姓名时，还需球队与别名共同核对。歧义保留为未匹配，不用模糊匹配强行关联。
- 原始时间保留，统一存 UTC 时间，页面解释用北京时间。赛程日期按来源和正确的美国东部时区处理，覆盖夏令时切换；不直接照搬现有固定 UTC-5 的简化逻辑。
- 比赛明细不以盘口为发现入口，避免漏掉没有报价的已结束比赛。

### 5.3 请求频率与失败处理

建议第一版使用以下保守默认值。这是项目自定限制，不是 ESPN 官方额度承诺：

| 参数 | 默认建议 |
| --- | --- |
| 同时请求数 | 1 |
| 两次请求间隔 | 至少 2 秒 |
| 单次网络超时 | 25 秒 |
| 小批验证上限 | 最多 30 次请求 |
| 正式单次任务上限 | 最多 100 次请求，所有尝试计数；达到后保存进度退出 |
| 自动重试 | 不自动重试；记录失败，修正后可针对失败项再运行 |
| 重复错误 | 同一错误累计两次仍未解决，停止该部分并报告，不循环请求 |
| 401/403/429 | 停止该来源的当前任务；记录拒绝/限流，不换代理绕过 |

采集期间显示请求数、发现比赛数、成功数、缺失数和失败原因。首版用本地任务锁防止两个任务同时更新同一索引。只有日志或手动启动命令，不新增公网采集接口。

日常更新建议只补新比赛和缺失比赛，并复查最近 3 个比赛日的已结束数据，接收供应商修正。旧赛季不每天重抓。历史回填按日期分批，优先当前赛季，其次上一赛季；不一次无限运行。

## 6. 分阶段执行与验收

阶段 1 已开始，尚未通过；阶段 2–5 未开始。同一批准范围内，验收通过即可进入下一阶段。需要付费、更换主要来源、扩大年份或改变核心方案时再确认。

### 阶段 1：环境检查与小批样本验证

**做什么：**

1. 检查当前分支、未提交文件、相关交接，避免干扰其他工作。
2. 在项目实际 Python 环境检查 HTTP 客户端初始化；核实并处理仍存在的代理解析问题。
3. 在 30 次请求上限内选取不同日期、不同球队、当前与上一赛季的小样本，目标检查至少 10 场已结束比赛。
4. 检查加时、未出场、延期/未结束、字段缺失等情况；找不到真实样例的边界，用明确标注的模拟样例验证解析，不声称真实覆盖。
5. 固定字段字典、赛事分类、错误状态与指标口径，报告哪些字段无法稳定取得。

**通过条件：**

- 项目环境能够实际发起免费请求；不是只有另一个脚本能联网。
- 样本能稳定识别比赛、双方球队、最终比分和球员记录；关键字段缺失逐项列出。
- 一般比赛样本的得分、投篮、篮板等与原始响应人工对照一致；异常有解释，不能靠补零通过。
- 来源限制或核心字段缺失影响方案时，停止扩大采集并提交调整建议。

**交付：** 小样本、字段说明、验证结果和明确的可用边界。

### 阶段 2：本赛季采集、保存与更新入口

**做什么：**

- 新增 ESPN 比赛列表与单场详情适配代码，单独放文件，避免破坏现有伤病功能。
- 实现原始响应、标准化明细、任务清单和索引，支持按日期采集、跳过已有完整比赛、续跑失败项。
- 提供独立命令入口，至少支持日期范围、请求上限、只补缺失、查看进度；使用说明写进 README。
- 从少量日期逐步补到 2026–27 赛季执行时的已结束比赛。日期边界由赛程确认，不猜测开赛日。

**通过条件：**

- 同一批重复执行，不重复计入比赛或球员统计。
- 中断后续跑只处理待完成项；请求上限、锁和限流停止行为有测试证据。
- 保存失败保留有效旧数据，状态明确说明更新失败和旧数据时间。
- 输出已扫描日期、发现/完成/缺失比赛、核心字段覆盖率及请求总数。
- 在有独立赛程可核对的范围对照漏场；仅核对已发现比赛时必须写“已发现比赛覆盖率”，不能声称全赛季完整。

**交付：** 可手动运行的免费数据采集能力及本赛季覆盖报告。

### 阶段 3：补上一赛季并计算摘要

**做什么：**

- 本赛季目标范围处理完、缺失清单明确后，按同样规则补 2025–26 赛季。
- 生成球队与球员的赛季、近 5 场、近 10 场摘要；球队增加主客场分项。
- 统计范围必须写明比赛阶段、截止时间、实际场数与缺失场数；上一赛季单列，不能悄悄补进本赛季平均值。
- 先实现下面这些指标；每个指标都有明确输入、单位、缺失处理和计算版本。

| 指标 | 第一版口径要求 |
| --- | --- |
| 胜负、场均得失分、净胜分 | 仅使用目标比赛之前已经结束的合格比赛，区分主客场和赛事阶段 |
| 投篮、三分、罚球命中率 | 用区间内总命中除以总出手；不能直接平均每场百分比 |
| 篮板、助攻、失误等 | 显示场均值和实际有效样本数；缺字段的场次不当作 0 |
| 球员出场与表现 | 分开计算球队比赛数、球员出场数及出场时场均表现；展示近期变化，不据此直接断言缺阵原因 |
| 估算回合数 | 阶段 1 固定基于出手、罚球、进攻篮板、失误的近似口径；双方输入缺失则不计算 |
| 估算攻防效率 | 按总得分/失分与合计估算回合计算每 100 回合表现，不直接平均每场比率 |
| 估算节奏 | 按实际比赛时长换算到 48 分钟；加时不清楚时标缺失，不按普通比赛硬算 |

**通过条件：**

- 用可手算样例核对比率、不同样本场数、加时、交易、未出场、重复和缺失处理。
- 近 5/10 场按实际比赛时间排序；不足 5/10 场显示实际场数。
- 重算结果能追溯到原始比赛和计算版本；同一输入结果一致。
- 本赛季与上一赛季分别报告覆盖情况；来源缺失不能被静默当成完整赛季。

**交付：** 历史明细、指标字典、可重算摘要与离线检查结果。

### 阶段 4：把数据接入聊天分析

**做什么：**

- 在选场或聚焦不超过 3 场时，附带相关球队摘要、球员近期使用情况和数据质量说明。
- 团队与球员明细全部保存，但聊天默认只取相关摘要；球队常用球员与已匹配伤病球员优先，明确截断规则。
- 新摘要可用时替代同口径的简版战绩，避免两份重复数字；缺少新摘要时可以使用旧战绩，但必须说明旧数据的区间与限制。
- 聊天只读已保存数据；资料不足时提示独立更新入口，不自动刷新盘口或在聊天请求里长时间采集。
- 修改提示词，要求区分事实、估算、假设；伤病状态必须带时间，不能把历史出场少直接解释成受伤。
- 按项目 `chat-prompt-maintenance` Skill 留新版本、CHANGELOG、回归样例和锁文件，并按 `codebase-map` Skill 更新相关代码地图。

**通过条件：**

- 离线构造选场和追问，证明正确球队的摘要确实进入模型输入。
- 比赛、平台隔离仍有效，模型看不到另一平台冒充所选平台的报价。
- 缺数据、更新失败、样本不足均可识别；不能把采集时间写成伤病发生时间。
- 新增正文摘要每场目标不超过 12,000 字符，最多 3 场；超过时按固定规则缩减并标记省略，缺失和时间说明不能被截掉。该上限是实施预算，验收报告实际大小。
- 离线测试与提示词校验通过。真实模型验证如获授权，单独记录完整回答是否成功、实际用量和引用是否准确；未做时标“模型效果未实测”。

**交付：** 数据已进入聊天的证据、提示词版本与验证结果。

### 阶段 5：交付数据质量报告，决定怎样调整分析

**做什么：**

- 汇总覆盖率、缺失字段、错误类型、更新耗时、磁盘占用与每次聊天摘要大小。
- 选取不少于 10 组不同情形的离线分析输入，核对新数据是否补上了原来的信息缺口；这是输入质量检查，不是命中率测试。
- 形成下一轮调整清单，例如哪些数据长期缺失、哪些指标重复、哪些球员变化值得展示。
- 若用户要验证预测效果，再单独确定前瞻记录和评估范围；本轮不顺带建设完整预测记录、结算与统计系统。

**通过条件：**

- 报告分别列出“已实现、真实取数已验证、只有离线验证、仍缺失”的内容。
- 没有历史盘口与赛前伤病时，不报告历史让分/大小分命中率或收益率。
- 不把少量比赛的表现当成调整权重的充分依据；未获得的新信息不由 AI 编造。

**交付：** 本轮交接、代码地图、操作说明，以及供用户审查的下一轮调整建议。

## 7. 防止历史数据让分析“提前知道答案”

这类问题通常叫数据泄漏：用赛后才知道的信息去预测赛前，结果会显得特别准，却不能用于真实分析。

- 每次生成摘要都指定目标比赛与截止时间，排除目标比赛本身、未来比赛和截止时尚未结束的比赛。
- 现在补抓的旧赛季统计，只能用于历史统计重建；采集时间保留为现在，不能伪造为比赛当时。
- 供应商后来修正的数据可能不同于当时发布值。缺少当时版本时，不能称为严格的历史时点验证。
- 当前伤病、当前球队归属不能套回历史比赛；球员历史数据按当场球队归档。
- 未来如做前瞻复盘，应在分析时保存摘要、盘口、伤病、提示词与回答版本，赛后另外追加结果。
- 上述前瞻复盘的完整产品功能属于后续范围，本轮只保留足够的数据版本与来源信息。
