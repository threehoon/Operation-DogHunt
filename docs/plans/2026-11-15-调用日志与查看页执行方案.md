## 2. 现状盘点结论（✅ 已完成）

### 2.1 日志只在终端里

- `backend/app/main.py` 的 `_configure_logging` 只给 `app.*` 配了终端输出（`StreamHandler`），终端一关就没了。根目录的 `backend_log.txt` 是 0 行的空文件。
- 现有日志共有十几处：聊天提示词版本（`services/chat/service.py`）、模型耗时（`integrations/llm.py`）、四个后台刷新函数（`services/odds/` 下的 `schedule`、`injuries`、`season`、`team_stats`），以及事件流意外失败。

### 2.2 一次调用的日志串不起来

一次聊天会先打出“提示词版本”，再打出“模型耗时”，两条之间没有共同编号。盘口更新会在后台线程里接着取赛程、伤病、效率和整季比分，这些日志也看不出是哪一次更新触发的。

### 2.3 出错原因被吞掉

- 四个后台刷新函数都写成 `except Exception: logger.warning("……未更新：意外错误")`，既没有异常类型，也没有出错的代码行。
- 外部接口（BALLDONTLIE、DunkAPI、The Odds API）成功的调用不记，耗时也不记；失败时抛出的错误带状态码，但只在上层汇总成一句话。
- 网页上看到的错误提示和后端日志之间没有对应关系，只能靠时间去猜。

### 2.4 密钥会出现在哪里（决定了脱敏规则）

| 来源 | 密钥位置 | 日志里要避开什么 |
| --- | --- | --- |
| 模型中转 | 请求头 `Authorization: Bearer …`，另有额外认证头 | 请求头、异常原文 |
| The Odds API（`scripts/fetch_nba_odds.py`） | **网址查询参数 `apiKey`** | 完整网址；httpx 的异常原文会带上网址 |
| BALLDONTLIE | 请求头 `Authorization` | 请求头 |
| DunkAPI | 请求头 `x-api-key` | 请求头 |

现有代码的做法是“只记异常类型、不记异常原文”，方向是对的。新方案沿用这个做法，再加一层按内容过滤的脱敏作为兜底。

## 5. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 密钥写进日志 | 不记网址和请求头是第一道防线，脱敏过滤是第二道，5.1 的测试和 5.2 的全目录搜索是第三道 |
| 聊天存档里有完整聊天内容 | 只存在本机 `data/traces/`，不进 Git，不出本机；查看接口只接受本机来源 |
| 日志越写越多 | 按天换文件、14 天清理、存档 200 次上限；单人使用估计每天不到 1 MB（未实测，阶段 5 记录实际大小） |
| 写日志拖慢聊天 | 每次调用只多写十几行，存档一次写一个文件；5.2 对比加日志前后聊天的首字时间 |
| `uvicorn --reload` 重启时多份日志配置 | 1.1 沿用现有“已配置就跳过”的判断，测试确认重复调用不会写两遍 |
