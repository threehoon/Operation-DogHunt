# 管理项目文件夹

让每个目录一眼能看出装了什么：同类文件放在一起，内容、记录、样例数据、生成物分开，入口文件留在目录根部。本 Skill 定规则和流程；项目已有的目录约定写在项目自己的目录说明里（`AGENTS.md` 指定的文件、`README`、代码地图），优先遵守那里的约定。

Skill 只在被调用时运行，不监听文件。

## 在 UMA 中使用

自然语言“整理 / 扫描目录”也可触发；先用 `skill` 按 `folder-organization` 加载。使用 `glob` 发现文件、`grep` 追踪引用、`read` 读取文本；下列扫描脚本通过 `bash` 在项目根目录运行，根目录含空格时用 `workdir` 指定，不拼接未引用的 `cd` 路径。脚本只需 Python 标准库，不为扫描安装依赖；`python3` 不可用时使用已确认存在的解释器，否则说明阻塞。

整理方案需要确认时使用可用的询问工具；未得到确认（包括跳过问题）不视为授权移动。执行移动前确认每个源与目标的绝对路径，涉及共享工作区时先协调文件归属。扫描报告只是分组候选，不是失败验收，也不能保证目录从此自动保持整洁。

## 什么时候用

- **新建文件前**：决定放在哪个目录、叫什么名字。
- **目录变挤**：扫描报告某个目录超出阈值，或新建文件会让它超出。
- **用户要求整理**某个目录或整个项目。

扫描命令（只读，不移动文件；路径可省略，默认当前目录）：

```sh
python3 .agents/skills/folder-organization/scripts/scan_layout.py [路径 ...] [--max-files 12] [--min-series 3] [--max-dated 50]
```

报告的是候选，不是结论；是否拆分按下一节判断。

## 判断目录该不该拆

出现以下任一情况，考虑分组：

- 一层直接文件超过约 12 个（不含 README、索引、`__init__.py` 这类入口文件）。
- 同一系列的多个版本平铺（`xxx_v1`…`xxx_vN` 至少 3 个），又和其他系列或文件混在一起。
- 文件名靠前缀区分类别（`chat_odds_*`、`chat_method_*`）：前缀就是该有一层目录的信号。
- 不同性质的文件混放：正式内容或源码，和记录类（CHANGELOG、issues、决策记录）、评测或样例数据、模板、生成产物在同一层。
- 按日期命名的日志超过约 50 个：可按月（`2026-11/`）分组；先确认交接或日志规则没有规定固定位置。

不拆的情况：

- 文件少于约 8 个，或全是同一种、彼此紧密相关的文件（例如一个组件的几个部件）。
- 源码目录刚过阈值、模块职责仍然单一：只记录，等职责真的分化再拆。
- 拆完的子目录只剩 1–2 个文件，且不会继续增长。

## 怎么分

1. **先沿用已有结构**：项目目录说明 > 同仓库相邻目录的做法 > 本节默认。
2. **按职责或种类分，不按扩展名分**；扩展名只在它本身就代表种类时才作分组依据。
3. **入口留在根部**：README、索引、锁文件或清单这类“读这个目录先看的文件”，以及被代码按固定路径读取的配置，留在原目录根部。
4. **版本系列一组一个子目录**：例如 `odds/chat_odds_v1.md`…`odds/chat_odds_v7.md`。移动时**只移动、不改名**，文件名和内容都保持原样，引用按名字找的地方才不会断。
5. **记录与内容分开**：记录类文件放 `records/`（或项目已有的同类目录）；评测、样例、快照放 `eval/` 或 `fixtures/`；生成产物放项目已有的产物目录或忽略掉。CHANGELOG 若被工具或约定要求放在根部，留在根部。
6. **层级浅**：从被整理的目录起最多再加两层。目录名用英文小写短名，风格与相邻目录一致（`snake_case` 或 `kebab-case`）。
7. 拆出 3 个以上子目录时，在目录根部的 README 里写一张简短结构表；原来就有 README 时更新它。

## 新建文件时

- 先看要放的目录和相邻目录已有哪些文件、怎么命名，照着放。
- 新文件会让目录触发上面的拆分条件时，照常把文件放在当前约定的位置，然后在交付时说明这个目录该整理了，附上建议的结构。**不在同一次改动里顺手整理**，除非用户要求。
- 已经分好组的目录，新文件直接放进对应子目录。

## 整理一个目录

移动文件会打断按路径找文件的代码、测试、链接和工具，所以先查清楚再动。

1. **定范围**：运行扫描，读目录里的文件和项目目录说明，确定这次只整理哪个目录。
2. **找全引用**：在整个仓库里搜索每个要移动的文件名和所在目录的路径，覆盖代码、测试、配置、构建与 CI 脚本、`.gitignore`、文档里的相对链接、其他 Skill 和锁文件。特别注意不写完整文件名的读取方式：
   - 目录常量加通配（`directory.glob("chat_*.md")`、`readdir`、`import.meta.glob`）；
   - 文件名正则、拼接路径（`dir / f"{name}.md"`）；
   - 代码模块的导入路径（移动 Python 模块要同步包结构和所有 `import`，移动前端模块要同步路径别名和导入）；
   - 锁文件、清单里记录的是文件名还是相对路径。
3. **出方案，等确认**：给出整理前后的目录树、每一处要改的引用（文件:行）、要跑的验证和风险。移动会改变用户的文件位置，**用户确认后再执行**。
4. **执行**：已跟踪的文件用 `git mv` 保留历史，未跟踪的用 `mv`。这一步只移动文件、改引用，不改文件内容、不顺手重构。带哈希的登记文件内容不变，只更新登记里的路径（如果登记的是路径）；能用工具重新生成的，用工具生成，不手改。
5. **验证**：
   - 再搜一遍旧路径，除历史记录外应当没有结果；
   - 运行与被移动文件相关的测试、构建或检查命令，结果原样报告；
   - 再跑一次扫描，确认目录已不在报告里。
6. **同步文档**：更新项目目录说明、目录根部的 README、引用这些路径的其他 Skill；项目使用代码地图时，按它的维护规则更新受影响的子块。历史记录（CHANGELOG 旧条目、交接文档）描述的是当时的情况，旧路径保留不改。

最后报告：整理了哪个目录、前后结构、改了哪些引用、验证结果、还没做的事。

## 不做的事

- 不在用户确认前移动、改名或删除文件。
- 不碰依赖目录、构建产物、本地运行数据、密钥文件和 `.git`。
- 不顺手改文件内容、重命名系列文件或重构代码。
- 不改历史记录里的旧路径。
- 不提交、不推送 Git。
